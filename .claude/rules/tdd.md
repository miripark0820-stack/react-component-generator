# TDD Rule

⚠️ **이 규칙은 Rigid — 상황에 맞게 변형하지 마라**

## 1. 적용 기준 구분

### TDD를 반드시 적용해야 하는 대상
- **비즈니스 로직**: 핵심 도메인 기능
- **API 엔드포인트**: 요청/응답 처리 로직
- **유틸리티 함수**: 재사용 가능한 헬퍼 함수
- **버그 수정**: 재발방지 테스트 먼저 작성

### TDD가 불필요한 대상
- **타입 정의**: interface, type alias
- **설정 파일**: config, environment setup
- **순수 UI 컴포넌트**: 렌더링만 담당하는 컴포넌트
- **SQL 쿼리**: 데이터베이스 스키마 관련

---

## 2. RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성
- **하나의 동작 = 하나의 테스트**
- **반드시 실행해서 실패 확인** (스킵하지 말 것)
- **실패 이유가 "기능 미구현"이어야 함** (문법 오류 등은 수정 후 재실행)
- 다른 테스트는 실패시키지 말 것

### GREEN: 최소한의 코드만 작성
- **YAGNI 원칙 준수** (You Aren't Gonna Need It)
- 테스트만 통과하는 최소 구현
- **신규 + 기존 테스트 모두 통과 확인**
- 과도한 최적화/일반화 금지

### REFACTOR: 중복 제거 및 개선
- **중복 제거**: 유사 패턴 통합
- **이름 개선**: 변수/함수명 명확화
- **헬퍼 추출**: 복잡한 로직 분리
- **GREEN 상태 유지** (모든 테스트 통과)
- **새로운 동작 추가 금지** (다음 RED로 이동)

### 반복
- 다음 동작에 대한 RED부터 재시작
- 모든 요구사항이 테스트로 정의될 때까지 반복

---

## 3. 삭제 강제 규칙

**테스트 전에 프로덕션 코드를 먼저 작성했다면:**
1. **해당 코드를 삭제**
2. RED 단계부터 재시작
3. "참고용"으로 남기는 것도 금지
4. 주석으로 보관하는 것도 금지

---

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순할수록 테스트가 빠르고 명확함. 버그는 단순한 부분에서도 발생 |
| "나중에 추가하겠다" | 나중은 없음. 기술부채는 복리로 증가. 지금 작성하는 것이 빠름 |
| "시간이 없다" | TDD는 시간을 버는 방법. 리팩토링/디버깅 시간 감소로 전체 속도 증가 |
| "삭제하면 낭비" | 작동하지 않는 코드는 이미 낭비. 테스트 있는 새 코드가 더 가치 있음 |
| "프로토타입이다" | 프로토타입도 버그 없어야 함. TDD는 동시에 문서화도 제공 |

---

## 5. 프로젝트별 규칙 우선 조항

**이 파일은 기본값(fallback)입니다.**

프로젝트 루트의 다음 파일 중 하나에 TDD 규칙이 명시되어 있으면:
- `CLAUDE.md`
- `AGENTS.md`
- `.claude/rules/` 내 프로젝트별 커스텀 파일

**그 규칙을 우선 적용합니다.**

이 파일의 규칙은 위 파일들이 없거나 해당 항목이 정의되지 않았을 때만 기준이 됩니다.

---

**작성 기준**: 엄격함 유지, 예외 최소화, 코드 품질과 팀 신뢰 향상
